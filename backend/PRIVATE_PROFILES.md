# Личные кабинеты клуба — защищённый контур

**Статус:** схема данных подготовлена; на GitHub Pages защищённые личные кабинеты **пока не работают**. Не использовать демонстрационный выбор ролей как подтверждение личности.

## Состав профиля
ФИО; игрок/тренер; позиция или должность; дата рождения; рост; вес; размеры джерси, бридж, футболки и шорт; игровой номер; уже подтверждённая фотография; четыре флага: медосмотр, РУСАДА, согласие, страховка.

Не импортировать: телефон, адрес, паспорт, загранпаспорт, прописку, комментарии, заболевание и любые другие сведения из исходных столбцов.

## Безопасное развертывание
1. Создать **закрытый** Supabase-проект или эквивалентный backend с HTTPS, Auth и PostgreSQL.
2. Применить backend/private_profiles.sql через защищённую администраторскую консоль.
3. Ввести приглашения администратором: каждому члену команды отдельная учётная запись, пароль задаёт сам пользователь, пароль не хранится в таблице или клиентском JavaScript.
4. Через защищённый API связать учётную запись и строку анкеты по утверждённому администратором соответствию. Самостоятельный выбор ФИО запрещён.
5. Права чтения: пользователь — только собственный профиль; дополнительные права тренера/АУП — только в отдельных RLS-политиках и серверных проверках. Редактирование четырёх флагов — только уполномоченным лицом по регламенту.
6. Импортировать из локального Excel только согласованные поля в **закрытую** базу после утверждения оснований обработки данных. Не коммитить roster.json, .xlsx, SQL INSERT с персональными данными или секреты.
7. Связать страницу входа с реальной auth API и проверкой сессии. До этого не показывать ложную форму «вход разрешён».
8. Протестировать: игрок A не может видеть игрока B даже прямым API-запросом; неавторизованный не получает ни одной записи; пароль не доступен клиенту; отзыв доступа блокирует сессию.

Публичные карточки болельщика и матчевая статистика остаются независимыми от закрытого профиля.
